📍 สรุปความคืบหน้า (Progress Summary) - โปรเจกต์ Supthavee ERP (อัปเดตถึง Phase 31.2 — พฤศจิกายน 2026)
สถิติภาพรวมปัจจุบัน:
- โครงสร้างฐานข้อมูล Master Data, เอกสารบัญชี และคลังสินค้า: [✅ ทำงานบน Supabase Cloud & Vercel Production 100%]
- สินค้าสำเร็จรูปและงานบริการ: 5,923+ SKUs (ตาราง `products` Schema Dump est_rows=6042) ผูกซัพพลายเออร์ `vendor_product_mapping` ประมาณ 6,357 แถว และทะเบียนวัตถุดิบโรงงาน `mst_materials` ประมาณ 22 รายการแยกจาก SKU เสื้อ

สิ่งที่เราทำสำเร็จร่วมกันในแชทนี้ (Architect Revisions):
1. Database Schema Reset: ตรวจพบปัญหาและทำการรันคำสั่ง SQL เคลียร์ข้อมูลขยะประเภทไร้รุ่นสินค้า (Orphaned Data) ออกจากตาราง `products` และ `product_models` สั่งตัดข้อมูลไฟล์ฝั่ง CSV เก่าทิ้งอย่างสมบูรณ์แบบ
2. Global Size Weight Alignment: ตรวจสอบและแก้ไขข้อบกพร่องของลำดับขนาดไซส์ในตาราง `mst_sizes` ยกเลิกระบบผูกตามแบรนด์เป็นแบบสากล (Global Size) พร้อมกำหนดชุดน้ำหนักลำดับ (sort_order) ตามลักษณะบิลและพฤติกรรมเสื้อผ้าของร้านจริง แยกกลุ่มขนาดเด็กอนุบาล (K), เด็กประถม (J), ไซส์ปกติผู้ใหญ่, กลุ่มไซส์ขยาย (XL/L) และขนาดตัวเลข (เบอร์ 1-72) ด้วยมาตราส่วน Gap of 10
3. Fixed-3 Character Color Standard: ยกระดับมาตรฐานการสร้าง Token สีกลางในตาราง `mst_colors` ให้บังคับล็อกความยาว 3 ตัวอักษรพิมพ์ใหญ่ (เช่น WHT, BLK, NVY) เพื่อบล็อกความไม่แน่นอนของความยาว SKU ช่วยให้ระบบยิงบาร์โค้ด และเขียน Regex ดักจับตัวอักษรของ AI OCR ทำงานได้แม่นยำสูงสุด
4. Database RLS Policy Insertion: จัดการปูพรมระบบความปลอดภัยระดับแถวข้อมูล (Row Level Security) ให้กับตารางการแมปรหัสสินค้าซัพพลายเออร์ (`vendor_product_mapping`) ปิดบั๊ก RLS Block Error ตอนทำคำสั่ง Bulk Insert
5. UI & Flow Specification: ออกแบบหน้าจอเวิร์กโฟลว์ Smart Goods Receipt (AI OCR) รูปแบบใหม่ โดยเปลี่ยนผ่านจากการคาดเดาโค้ดล่วงหน้า ให้เป็นการสกัดโค้ดดิบจริงจากกระดาษ (`raw_vendor_sku`) แล้วเปิดระบบจับคู่แบบ On-the-fly หน้างานเพื่อความยืดหยุ่นในการปฏิบัติงานจริง
6. Environment & Security Stabilization: วางระบบแยก Environment ระหว่าง Local และ Production อย่างเด็ดขาดผ่านระบบ Supabase Migrations รวมถึงแก้ไข RLS Policies และสิทธิ์ระดับตาราง (`GRANT SELECT`) ทำให้ UI สามารถคิวรี Master Data เช่น ตาราง `contacts` ผ่าน `anon` role ได้สำเร็จอย่างปลอดภัย
7. Smart Bulk Matrix Mapping: สร้างระบบผูกรหัสซัพพลายเออร์สำเร็จ 100% รองรับการ Custom Pattern รหัสได้อย่างอิสระ และใช้ Accordion Grouping เพื่อให้ง่ายต่อการใช้งาน
8. Architecture Pivot (Zero Client-Side Fetching): แก้ปัญหา RLS Permission Denied แบบถอนรากถอนโคน โดยการถอดการคิวรีผ่านหน้าบ้าน (Client) ออกทั้งหมด และบังคับใช้ Server Actions ร่วมกับ Service Role Key (supabaseAdmin)
9. Overwrite Protection: เพิ่มระบบ Guardrail (UX/UI) ดักจับและแจ้งเตือนพนักงาน หากมีการพยายามกด Save ทับสินค้ารุ่นที่เคยทำการ Mapping ไว้แล้ว เพื่อป้องกัน Human Error
10. On-the-fly Product Creation (Quick Create): สร้างระบบเพิ่มสี/ไซส์กลางอากาศระหว่างรับของเข้า โดยดึงข้อมูล Master Data ทะลุกำแพง RLS ผ่าน Server Actions พร้อมระบบ Auto-fill เพื่อลด Human Error
11. Environment Synchronization: วางกระบวนการ Seed Data จาก Cloud สู่ Local อย่างถูกต้องผ่าน Supabase CLI (db dump & reset) เพื่อให้ Master Data ตรงกัน 100% พร้อมทดสอบระบบ
12. Strict Zero Client-Side Fetching Enforcement: ค้นหาและทำลายโค้ด Client-side `supabase.from()` ที่ซ่อนอยู่ในไฟล์ Utility ทิ้ง 100% เพื่อขจัดบั๊กผีหลอก (Ghost Bug) และ Turbopack Cache Error อย่างเด็ดขาด
13. Smart Goods Receipt OCR Enhancement: อัปเกรด Edge Function (Gemini) ให้อ่านเลขที่เอกสารและวันที่เอกสารอัตโนมัติ โดยใช้คำใบ้จาก `ocr_pattern_config` ป้องกันการเดาสุ่ม
14. UPSERT Mapping Protection: แก้ปัญหาระบบ Error เวลายืนยันสินค้ารหัสซ้ำซ้อนในบิลเดียว ด้วยการเปลี่ยนคำสั่งบันทึก Mapping เป็น `UPSERT`
15. Duplicate Invoice Early Warning: สร้างระบบแจ้งเตือนบิลซ้ำซ้อนแบบเรียลไทม์ (Composite Key: `vendor_id` + `document_number` + `document_date`) ก่อนการบันทึกเข้า Ledger เพื่อรองรับบิลเงินสดที่รันเลขใหม่รายเดือน
16. System Guardrails & Git Checkpoint: ทำการ Start ระบบ Git Repository ภายในเครื่อง และสร้างไฟล์ `.cursorrules` เพื่อล็อกสถาปัตยกรรมโค้ดที่เสถียร ป้องกัน AI Code Regression (AI รื้อโค้ดจนพัง)
17. Net Cost Apportionment Engine: สร้างระบบ Pure Math Engine คำนวณและกระจายต้นทุนสุทธิ ป้องกันปัญหาเศษสตางค์ (Decimal Leakage) ครอบคลุมการคำนวณของแถม ส่วนลดเหมาบรรทัด ส่วนลดขั้นบันได และ Prorate ส่วนลดท้ายบิล
18. Goods Receipt UI Enhancement: ปลดล็อกและผสาน UI หน้า Goods Receipt รองรับ Checkbox ของแถม และเปิดช่องกรอกส่วนลดท้ายบิล พร้อมแสดง Real-time Preview ต้นทุน
19. Auto-Update Last Purchase Price (LPP): เขียน Server Action ให้นำต้นทุนสุทธิสุดท้าย (Final Unit Cost) วิ่งกลับไป UPDATE ทับที่ตาราง `products` (`cost_price`) อัตโนมัติทุกครั้งที่รับของเข้า
20. Product Matrix UI Data Integrity Guard: ล็อกสิทธิ์ไม่ให้ผู้ใช้กรอก Sort Order ไซส์เอง เปลี่ยนเป็นระบบดึงรายการไซส์มาตรฐานมาให้ติ๊กเลือกเท่านั้น เพื่อรักษามาตรฐาน Global Size และรองรับการเลือก "ราคาเน็ต" (Net Price) ทันทีตอนสร้าง SKU
21. OCR Matching UI Fix: แก้ไข Dropdown เลือกสินค้าในหน้า OCR ให้แสดงผลแบบ Text Wrap ป้องกันชื่อสินค้ายาวโดนตัดคำ ลดความสับสนของพนักงาน
22. Advanced Sales Document Architecture (Phase 4): วางระบบสถาปัตยกรรมฐานข้อมูลสำหรับเอกสารขายและซื้อทั้งหมด (Header & Line Items) พร้อมรองรับการระบุผู้ติดต่อ (Contact Persons) แบบ On-the-fly
23. Atomic Auto-Numbering Generator (Phase 4): สร้าง PostgreSQL RPC Function เพื่อรันเลขที่เอกสารแบบ Lock Table ป้องกันปัญหาเลขบิลซ้ำซ้อน (Race Condition) ได้ 100%
24. Cost Snapshot & Profit Analysis (Phase 4): สร้างระบบ Snapshot ดึงราคาต้นทุนปัจจุบัน (LPP) มาฝังไว้ที่รายการบิลทันทีที่เปิดบิลขาย เพื่อล็อกต้นทุนที่แท้จริง ณ วินาทีนั้น
25. Document Summary Engine (Phase 4): สร้างระบบคำนวณภาษีมูลค่าเพิ่ม (INCLUSIVE, EXCLUSIVE, NONE) และประมวลผลส่วนลดท้ายบิลแบบ Real-time พร้อมถอดฐานภาษีได้อย่างแม่นยำ
26. Ledger-Driven Inventory Deduction (Phase 4): พัฒนาระบบตัดสต็อกขาออกแบบ OUT โดยบันทึกลง `inventory_ledger` ตามเงื่อนไขประเภทเอกสาร แทนการแก้ไขตาราง `products` ตรงๆ เพื่อรักษา Data Integrity
27. URL-Based Data Filtering (Phase 4): สร้างหน้ารวมประวัติเอกสาร (Document List) พร้อมระบบกรองข้อมูล (Filter) ผ่าน URL Search Parameters รักษาโครงสร้าง Zero Client-Side Fetching
28. Document Conversion & Lineage (Phase 4): สร้างระบบแปลงเอกสาร (เช่น QT -> INV_DO) พร้อมรันเลขใหม่และผูกสายสัมพันธ์ `ref_document_id` ไว้ตรวจสอบย้อนหลังทางบัญชี
29. Minimalist Print Layout (Phase 4): สร้าง Component สำหรับการสั่งพิมพ์เป็นเอกสารบิล (A4) ผ่าน Browser ด้วย CSS `@media print`
30. AI Document Intelligence (Phase 3/4 Bridge): อัปเกรด Prompt ให้ Gemini Vision ให้อ่านและวิเคราะห์ "ประเภทเอกสาร" (`doc_type`) และ "ประเภทภาษี" (`vat_type`) อัตโนมัติ เพื่อทำ Auto-fill หน้า OCR (Human-in-the-loop)
31. Manual Goods Receipt & Attachment (Phase 3/4 Bridge): สร้างระบบรับสินค้าเข้าคลังแบบกรอกข้อมูลเอง (Manual) พร้อมเชื่อมระบบแนบไฟล์ภาพบิลผ่าน Supabase Storage (Document Image Attachment)
32. Document Taxonomy Refactor (Phase 5): รื้อโครงสร้างและจำแนกประเภทเอกสารให้ตรงตามมาตรฐาน ERP แยกกลุ่ม Sales ('QT', 'INV_DO', 'TAX_INV', 'CS_TAX', 'ABB', 'DEP_IN', 'REC', 'CN') และ Purchases ('PO', 'AP_TAX', 'AP_INV', 'AP_CASH', 'DEP_OUT', 'PAY') อย่างเด็ดขาด
33. AR/AP Dashboard Initialization (Phase 5): สร้างหน้า Dashboard ระบบลูกหนี้และเจ้าหนี้ โดยดึงยอดค้างชำระจาก `grand_total` (รวม VAT) แบ่งเป็น 2 แท็บ เพื่อแสดงภาพรวมสภาพคล่อง
34. Payment Knock-off Foundation (Phase 5): วางโครงสร้าง UI และ Server Action รองรับการรับชำระเงินและตัดยอดหนี้ (Knock-off Allocation) แบบ Zero Client-Side Fetching
35. Advanced Bulk Payment Engine (Phase 5): อัปเกรดหน้าตาราง AR/AP Payment ให้รองรับ Checkbox สำหรับตัดยอดหลายบิลพร้อมกัน (Auto-fill Outstanding Amount) พร้อมระบบเลือกทั้งหมด (Select All)
36. Storage Integration for Financial Docs (Phase 5): ประยุกต์ใช้ Supabase Storage สร้างระบบอัปโหลด "สลิปโอนเงิน" และ "หนังสือรับรองการหักภาษี ณ ที่จ่าย (WHT)" ผูกกับเอกสารประเภท PAY และ REC
37. Cross-Reference Document Search (Phase 5): อัปเกรด Server Action ให้รองรับการค้นหาบิลฝั่ง AP ด้วย "เลขที่เอกสารภายใน" (Internal No.) และ "เลขอ้างอิงผู้จำหน่าย" (Vendor Ref No.) แบบ OR Logic
38. Document Lineage UI Overhaul (Phase 5): ปรับปรุงหน้าแสดงรายละเอียดเอกสารประเภทการเงิน (PAY/REC) ให้ซ่อนตารางสินค้า และแสดงตาราง "รายการเอกสารที่ตัดชำระ (Allocated Documents)" แทน เพื่อความถูกต้องทางบัญชี
39. Interactive Receipt Tracking (Phase 5): สร้างระบบ Migration เพิ่มคอลัมน์ `original_receipt_received` และสร้างปุ่ม Interactive Toggle เพื่ออัปเดตสถานะ "รอเอกสาร/รอออกเอกสาร" เป็น "ได้รับแล้ว/ออกเอกสารแล้ว" แบบเรียลไทม์
40. Financial Print Templates (Phase 5): ออกแบบ Layout สำหรับการพิมพ์ใบเสร็จรับเงิน (REC) และใบจ่ายชำระหนี้ (PAY) พร้อมปุ่มสั่งพิมพ์ที่ซ่อน UI ที่ไม่จำเป็นผ่าน `@media print`
41. Deposit Management Foundation (Phase 5): สร้าง Dashboard และฟอร์มสำหรับรับเงินมัดจำ (DEP_IN) และจ่ายมัดจำ (DEP_OUT) ควบคุม State การสลับแท็บผ่าน URL Search Params
42. Deposit Allocation Engine (Phase 5): นำยอดมัดจำคงเหลือ (Available Deposit) ไปแสดงในฟอร์มรับ/จ่ายชำระเงิน (AR/AP Payment) พร้อมระบบคำนวณยอดอัตโนมัติ (Math.min) และหักลบยอดชำระจริง (Net Payment) แบบเรียลไทม์
43. Standardized REC/PAY Value (Phase 5): อัปเกรดระบบให้การบันทึกเอกสารใบเสร็จ (REC/PAY) แสดงยอด Grand Total ตรงตามมูลค่าหนี้ที่ตัดจริง และแสดงรายการมัดจำที่ใช้ตัดเป็นยอดติดลบ (Deduction) ตามหลักบัญชี
44. Strict AR/AP Refund & Write-off Separation (Phase 5): เพิ่ม Database Migration สร้างประเภทเอกสาร 'AR_REFUND', 'AP_REFUND', 'AR_WRITEOFF', 'AP_WRITEOFF' พร้อมการรันเลขแยกอิสระ (SRF, PRF, SWO, PWO) ป้องกันการนำกระแสเงินสดมาปะปนกัน
45. Deposit Management Actions (Phase 5): สร้างระบบคืนเงิน (Refund) และ ตัดเศษบัญชี (Write-off) แบบมีเอกสารอ้างอิงทางการเงิน ผูกสายสัมพันธ์กับมัดจำต้นทางผ่าน `document_allocations` พร้อมรองรับการแนบไฟล์สลิปโอนเงิน
46. VAT Inheritance on Refunds (Phase 5): พัฒนาระบบให้เอกสาร Refund และ Write-off สืบทอดประเภทและอัตราภาษีมูลค่าเพิ่ม (VAT Type/Rate) จากมัดจำต้นทาง พร้อมถอด VAT อัตโนมัติตามหลักภาษีสรรพากร
47. Deposit Print Templates (Phase 5): สร้าง Layout การพิมพ์สำหรับ "ใบสำคัญจ่ายเงินคืน (Refund Payment)", "ใบสำคัญรับเงินคืน (Refund Receipt)", และ "ใบสำคัญปรับปรุงบัญชี (Income/Expense Adjustment)" เพื่อรองรับการทำ Audit Trail เต็มรูปแบบ
48. Billing Note Foundation (Phase 5): สร้างสถาปัตยกรรม `billing_note_items` เป็น Junction Table สำหรับจัดกลุ่ม Invoices ที่ค้างชำระ โดยไม่ส่งผลกระทบต่อบัญชีแยกประเภท (GL)
49. Zero Client-Side Billing UI (Phase 5): พัฒนาหน้า Create Billing Note ด้วย URL Search Params พร้อมระบบสรุปยอดลูกหนี้/เจ้าหนี้ที่มียอดค้างชำระอัตโนมัติโดยไม่ต้องเดาสุ่ม
50. OCR Resiliency Engine (Phase 3 Upgrade): อัปเกรด Edge Function ของ Gemini Vision เพิ่มระบบ Model Cascade Fallback (gemini-3.6-flash -> 3.5-flash -> 2.5-flash) พร้อม Exponential Backoff Retry ดักจับ Error 503/429
51. Payment Allocation with Billing Note (Phase 5): เชื่อมสะพานให้หน้าจอรับ/จ่ายชำระเงิน (REC/PAY) สามารถดึงเอกสารลูกข่ายทั้งหมดจาก "ใบวางบิล (BN/BR)" มาทำ Knock-off ตัดหนี้ด้วยวิธี FIFO ได้อัตโนมัติ
52. Master Data Quick Edit & Radix UI Fix: แก้ไขปัญหา Focus Trap ของ Nested Modal (Shadcn) ในหน้า Contact และเพิ่มปุ่ม Quick Edit ลูกค้าแบบ On-the-fly ในหน้าฟอร์มเปิดบิล
53. Accounting Standard - Late Numbering: เปลี่ยนสถาปัตยกรรมการรันเลขที่เอกสารจากการรันทันที เป็นการใช้รหัส DRAFT (DRAFT-YYYYMMDDHHmmss) และรันเลขจริง (RPC) เมื่อกดยืนยัน (ISSUED) เพื่อป้องกันเลขที่เอกสารสูญหาย/แหว่งตามมาตรฐานสรรพากร
54. Accounting Standard - Cancel & Replace: วางระบบยกเลิกเอกสาร (Void) พร้อม "คืนสต็อก (Inventory Reversal)" อัตโนมัติ และระบบ "ออกเอกสารทดแทน" ที่โคลนข้อมูลมาสร้าง DRAFT ใหม่พร้อม Auto-Remark อ้างอิงเอกสารที่ถูกยกเลิก (Audit Lineage)

56. Strict Document Guardrails: ล็อกสิทธิ์การแก้ไขรายการสินค้าและยอดเงิน (Disable Inputs) หากเอกสารนั้นเป็น "เอกสารออกทดแทน" อนุญาตให้แก้ไขได้เฉพาะชื่อ/ที่อยู่ลูกค้า และหมายเหตุ เพื่อรักษาความถูกต้องของยอดเงินตามหลักบัญชี

Subcontracting Line Item Assignment (Phase 13 Upgrade): รื้อสถาปัตยกรรม Kanban จากการระบุช่างเหมารวมทั้งใบงาน เป็นการระบุช่าง (Technician) และต้นทุนค่าแรง (Wage Cost) แยกเป็นรายบรรทัด (Line Item) ในตาราง `document_items` เพื่อรองรับงานบริการหลายประเภทในบิลเดียว (เช่น สกรีน, ปัก) ให้ช่างแยกกันทำงานได้อย่างอิสระ
112. Ambiguous Foreign Key Resolution (Phase 13 Upgrade): ขจัดปัญหา Error 500 (Could not embed) โดยการเขียน Explicit Join (`!document_id`) บังคับให้ Supabase PostgREST เลือกเส้นทาง Foreign Key ที่ถูกต้อง ป้องกันความสับสนระหว่างการโยงบิลขายและใบสรุปวางบิลช่าง
113. Enterprise Stock Adjustment (Phase 14): พัฒนาระบบ Cycle Counting รองรับเอกสาร STK_OB (ยอดยกมา) และ STK_ADJ (ปรับปรุงสต็อก) บันทึกผ่าน `inventory_ledger` พร้อมระบบคำนวณส่วนต่าง (Physical Inventory Variance) อัตโนมัติ ป้องกันพนักงานคำนวณผิดพลาด
114. Advanced Sales Document Lineage: รื้อสถาปัตยกรรมเอกสารขายเป็น `QT -> SO -> MTO/Delivery` บังคับให้เริ่มการขายด้วย QT และใช้ SO เป็นจุดศูนย์กลาง
115. Soft Allocation (ATP) Engine: สร้างระบบจองสต็อกบนเอกสาร SO โดยกันยอด Available Stock ทันทีที่ SO ถูก Issue เพื่อป้องกันการขายสินค้าซ้ำซ้อน (Race Condition) สำหรับงานสั่งผลิต
116. Multi-Service Subcontracting UI: อัปเกรดหน้าต่างสร้างใบสั่งผลิต (MTO) ให้รองรับการเลือกประเภทงานแบบ Multi-select (เช่น สกรีน + ปัก ในใบงานเดียว)
117. Expense OCR Cloud Resiliency: อัปเกรด Edge Function ฝั่งค่าใช้จ่าย แก้ปัญหา Payload Size Limit (ขยายเป็น 5MB), ขยาย Timeout เป็น 60s, ล้าง Markdown Code Block อัตโนมัติ, และอุดรอยรั่ว JWT Auth (Missing sub claim) สำเร็จ
118. Seamless Accounting UI/UX: ปรับตาราง Contacts ให้อ่านง่ายแบบ Single-line และเพิ่มระบบ URL-Driven Slide-over Sheet ดึงรายละเอียดใบสั่งผลิต (Job) ดูทะลุจากหน้าสรุปวางบิลช่าง (TB) ได้ทันทีโดยไม่หลุดโฟลว์การทำงาน
119. Cloud-First Database Alignment (Phase 14): ปรับสถาปัตยกรรมการจัดการ Database เป็นการอัปเดต Schema ตรงบน Supabase Cloud และดึง Types กลับ Local เพื่อแก้ปัญหา Schema Drift บน Vercel
120. Period Lock Dashboard (Phase 14): สร้างระบบปิดรอบบัญชีรายเดือน (`accounting_periods`) พร้อมสวิตช์ Toggle ตรวจสอบสิทธิ์ระดับ Admin ป้องกันการแก้ไขเอกสารข้ามงบตามหลัก Cut-off (GAAP)
121. Approval Workflow & Maker-Checker (Phase 14): สร้าง Approval Center แบบ Slide-over ควบคุมการอนุมัติเอกสารมูลค่าสูง (Expenses > 5,000) เอกสารที่ถูกปฏิเสธจะคงสถานะ DRAFT (บังคับใส่เหตุผล) ส่วนเอกสารที่อนุมัติจะเปลี่ยนเป็น ISSUED และรันเลขจริงทันที พร้อมบันทึกประวัติลง `approval_logs` และ `audit_logs` สมบูรณ์
122. AP Installment Engine (Phase 14): สร้างระบบผ่อนชำระแบบ TFRS 16 แยกระหว่างเงินต้น (ราคาทุน) และดอกเบี้ย พร้อมระบบ Auto-Split หารค่างวดและปัดเศษสตางค์ลงงวดสุดท้ายอัตโนมัติ
123. AP Auto-Clearing Standard (Phase 14): อัปเกรด Constraint ของตาราง Expenses ให้รองรับสถานะ 'PAID' และเขียน Logic ให้บิล Cash Purchase วิ่งเข้าสถานะ PAID ทันทีที่อนุมัติ
124. Installment Knock-off (Phase 14): สร้างระบบ Payment Allocation ตัดหนี้รายงวดเชื่อมโยงระหว่างตาราง `payment_transactions` และ `expense_installments` หากจ่ายครบทุกงวดระบบจะปิดบิล EXP เป็น PAID อัตโนมัติ
125. Direct Capitalization Workflow (Phase 14): แก้ปัญหา React UI Crash จาก Native Date Input โดยเปลี่ยนวิธีเชื่อมโยงบัญชีพักสินทรัพย์ (Asset Clearing) ให้ยิง URL Search Parameters จากหน้า Expense Detail ไปหาฟอร์ม Fixed Asset โดยตรงเพื่อความเสถียร
126. Server Component Boundary Fix (Phase 14): อุดรอยรั่วสถาปัตยกรรม Next.js ដោយการถอด Client Event Handlers (`onClick`) ออกจากไฟล์ Server Component (`page.tsx`) และบังคับใช้ `<Link href...>` แก้ปัญหา Vercel Render Error สำเร็จ 100%
127. Duplicate Asset Registration Prevention (Phase 14): พัฒนาระบบตรวจสอบและซ่อนปุ่ม "ขึ้นทะเบียนสินทรัพย์" ในหน้าเอกสาร Expenses ทันทีที่บิลใบนั้นถูกนำไปขึ้นทะเบียนเป็น Fixed Asset เรียบร้อยแล้ว เพื่อป้องกันปัญหา Human Error ในการบันทึกทรัพย์สินซ้ำซ้อน
128. Asset Clearing Compliance (Phase 14): ล็อก Business Logic ให้เอกสาร Expenses ยังคงเก็บประวัติหมวดหมู่ "พักสินทรัพย์รอขึ้นทะเบียน (Asset Clearing)" ไว้เสมอ แม้จะนำไปขึ้นทะเบียนแล้ว เพื่อรักษาสายสัมพันธ์ข้อมูลและ Audit Trail ต้นทางตามมาตรฐาน GAAP/TFRS
129. Human-Readable Audit Trail Engine (Phase 14): อัปเกรดระบบ Audit Trail เพื่อทำการ Parse JSONB (old_data/new_data) และประยุกต์ใช้ Business Dictionary Mapping เปลี่ยนชื่อคอลัมน์ให้อ่านง่ายสำหรับผู้บริหารและนักบัญชี (เช่น `net_amount` -> 'ยอดก่อนภาษี') พร้อมกรอง False Positives
130. URL-Driven Asset Details (Phase 14): ออกแบบและพัฒนาระบบ Slide-over Sheet สำหรับดูรายละเอียด Fixed Asset แบบเจาะลึกผ่าน URL Search Params (`?view_asset_id=...`) ปฏิบัติตามมาตรฐาน Zero Client-Side Fetching พร้อมเปลี่ยนจากการแสดงผล UUID เป็นการแสดงเลขที่เอกสาร (`document_no`) เพื่อความสมบูรณ์ของ UX/UI
131. Vercel Client/Server Boundary Enforcement (Phase 14): แก้ปัญหา Build Error บน Vercel โดยการแยก Component ที่พึ่งพา React Context อย่างเด็ดขาด (`AssetDetailSheet`) เป็น Client Component และรักษาหน้า Page ให้เป็น Server Component บริสุทธิ์
132. Fixed Asset Depreciation Engine (Phase 14): พัฒนา RPC Function (`calculate_monthly_depreciation`) คำนวณค่าเสื่อมแบบเส้นตรง (Straight-line) ป้องกันเศษสตางค์แหว่ง พร้อมระบบ Proration คำนวณเฉลี่ยรายวันสำหรับเดือนแรกที่ซื้อทรัพย์สินตามหลัก GAAP
133. Depreciation Ledger UI (Phase 14): สร้างตาราง `asset_depreciation_ledger` เก็บประวัติการตัดค่าเสื่อมรายเดือน และแสดงผลบน Slide-over Sheet แบบ Zero Client-Side Fetching
134. Global Thai Date Standard (Phase 14): กำหนดมาตรฐานแสดงผลวันที่หน้า UI เป็น พ.ศ. เสมอ ผ่านฟังก์ชัน `formatThaiDate(date, 'short'|'long')` เพื่อป้องกันการสับสนระหว่าง ค.ศ. และ พ.ศ.
135. Data Access Scope (Phase 14 ABAC): เพิ่มโครงสร้าง Ownership (`created_by`) ในตารางเอกสาร และกำหนดขอบเขต `data_access_scope` ('ALL' / 'OWN') ใน `user_profiles` พร้อม RLS Policy ล็อกการมองเห็นเอกสาร
136. Permission Matrix (Phase 14 ABAC): อัปเกรดระบบสิทธิ์ด้วยฟิลด์ `accessible_modules` (JSONB) ใน `app_roles` พร้อม UI เปิด/ปิดสิทธิ์ 5 โมดูลหลัก (sales, purchases, inventory, finance, settings) และ Middleware Auth Guard ตามหลัก SoD ของ ERP ระดับโลก
137. DoA Approval Limit Guardrail (Phase 14 ABAC): เพิ่มฟิลด์ `approval_limit` ในโปรไฟล์ เพื่อล็อกและบังคับเอกสารที่มีมูลค่าสูงเกินอำนาจเข้าสู่ระบบ PENDING (Maker-Checker) โดยตั้งค่า Admin ให้มีลิมิต 999,999,999.00 บาทแทนการ Bypass โค้ด
138. Pre-Phase 15 Architecture: เตรียมโครงสร้างสถาปัตยกรรมรองรับค่าขนส่งต้นทาง (Freight-In) โดยเพิ่ม `freight_cost` ระดับ Header เพื่อเตรียมรองรับ Landed Cost ตามหลัก GAAP
139. Roadmap Extension (Phase 15-17): กำหนดทิศทางโมดูลใหม่ 3 แกนหลัก ได้แก่ 1. Inventory & Material Management, 2. Production Kanban & WIP, และ 3. AR & Order-to-Cash เพื่อปิดวงจรธุรกิจ B2B ครบถ้วน
140. Enterprise Category Normalization (Phase 13 Upgrade): รื้อและอัปเกรดโครงสร้างตาราง `mst_categories` ให้รองรับความสัมพันธ์แม่-ลูก (Hierarchical) แบบ 1 ตัวอักษรสำหรับหมวดหมู่หลัก (Parent) และ 2 ตัวอักษรสำหรับประเภทย่อย (Child) ตามมาตรฐาน Significant Coding ของ ERP
141. Raw Material & Service Size Standardization (Phase 13 Upgrade): เพิ่มรหัสไซส์มาตรฐาน `00` (N/A ไม่มีไซส์) ลงใน `mst_sizes` และปรับ UI ให้ล็อกไซส์นี้อัตโนมัติเมื่อสร้างวัตถุดิบ เพื่อป้องกันขยะข้อมูล (Data Pollution) ปะปนกับไซส์เสื้อผ้าสำเร็จรูป
142. Non-Inventory Service Engine (Phase 13 Upgrade): เพิ่มแฟล็ก `is_service` ควบคู่กับ `is_raw_material` ในตาราง `product_models` เพื่อแยกระหว่างงานบริการ (คิดเงินลูกค้าแต่ไม่ตัดสต็อก) ออกจากวัตถุดิบ (ไม่โผล่ในบิลขายแต่เบิกตัดสต็อกได้) ตามมาตรฐาน TFRS 15
143. Smart SKU Picker Service Exemption (Phase 13 Upgrade): อัปเดต Server Action ค้นหาสินค้าในหน้าเปิดบิลขาย ให้ฟิลเตอร์ซ่อน Raw Material ทั้งหมด แต่ยอมให้แสดงรายการที่เป็น `is_service = true` เพื่อให้เซลส์สามารถแอดงานสกรีน/งานปักลงในบิลขายพร้อมเสื้อผ้าสำเร็จรูปได้
144. Advanced BOM Engine (Phase 16): สร้างระบบสูตรการผลิต (Bill of Materials) ผูกสินค้ารุ่น (Finished Goods) เข้ากับวัตถุดิบ (Raw Materials) พร้อมคำนวณ %เผื่อเสีย และดึงต้นทุนล่าสุดประเมินล่วงหน้า
145. UI Focus Trap Resolution (Phase 16): แก้ปัญหา ComboBox ซ้อนทับใน Dialog (Radix UI) ด้วยการตั้งค่า modal={true} ทำให้ช่องค้นหาวัตถุดิบกางออกได้สมบูรณ์
146. Enterprise Kanban Architecture (Phase 16): พัฒนากระดานลากวาง 4 สถานะ (PLANNED, IN_PROGRESS, QA, COMPLETED) ทำงานด้วย Optimistic UI และ Zero Client-Side Fetching
147. MTO Data Integrity (Phase 16): ออกแบบตาราง production_jobs, production_job_items, และ production_job_materials ให้รองรับการจัดเก็บรูปภาพ Mockup, ข้อความหมายเหตุ, และแยกไซส์งานเย็บได้อย่างละเอียด
148. Slide-over Job Details (Phase 16): สร้างหน้าต่าง Sheet ขับเคลื่อนด้วย URL Params (?jobId=) สำหรับดูใบงานการผลิต แจกแจงจำนวนที่ต้องเย็บ (SKU) และวัตถุดิบที่ต้องเบิก (WIP) ในหน้าเดียว
149. Database Cloud-First Rule Enforcement: ยืนยันการทำงานบน Supabase Cloud 100% เลิกใช้ Local Migrations ที่สร้างจาก AI เพื่อป้องกัน Schema Drift และ Error "Relation already exists"
150. Architecture Pivot - SO Driven Production (Phase 17 Transition): เปลี่ยนกระบวนทัศน์จากการเปิดใบสั่งผลิตแบบ Manual บนหน้า Kanban ไปเป็นการให้ Sales Order (SO) เป็นจุดยิงคำสั่ง (Trigger) ดึงรูป Mockup และจำนวนไซส์ ทะลุเข้า Kanban อัตโนมัติ เพื่อรักษา Job Costing และ Matching Principle (GAAP)
151. Routing & Yield Confirmation Engine (Phase 17): สร้างตาราง `production_job_operations` เป็นศูนย์กลางควบคุมต้นทุนผลิตภายใน (In-house Routing) พร้อมระบบ UI ดึงยอดผลิตคาดการณ์ (Planned Yield) และดักจับความคลาดเคลื่อน (Variance Guardrail) บังคับใส่หมายเหตุเมื่อยอดผลิตจริงไม่ตรงเป้าหมาย
152. Auto-Confirmation (Backflushing) Pipeline (Phase 17): ปรับสถาปัตยกรรม Kanban ให้ผูกสถานะ Routing เข้ากับการลากการ์ด เมื่อหัวหน้างานย้ายการ์ดไปสถานะ 'COMPLETED' ระบบจะเคลียร์งานย่อยให้เสร็จสิ้น และส่งยอดค่าแรงทั้งหมดเข้าสู่ระบบวางบิลช่าง (TB) อัตโนมัติ ลดปัญหา Double Data Entry
153. Decoupled Fetching Architecture (Phase 17): อุดรอยรั่ว PostgREST Schema Cache Error (Could not find a relationship) บริเวณ Slide-over Sheet โดยเปลี่ยนจากการ Join ตรงใน Query เป็นการดึงข้อมูล 2 จังหวะอิสระแล้วทำ Data Merging ฝั่ง Server แทน การันตีความเสถียร 100%
154. Document Conversion Engine (Phase 17 Completion): พัฒนาระบบแปลงเอกสารขาย (SO -> INV_DO / TAX_INV) แบบ Push Method จากหน้า Detail รักษา Lineage `ref_document_id` ไว้ตรวจสอบย้อนหลัง 100%
155. Material Backflush Decimal Precision (Phase 17 Completion): อัปเกรดฐานข้อมูลคอลัมน์ `qty` ของตารางคลังสินค้าและเอกสารเป็น `NUMERIC(14,4)` และแก้โค้ด Server Action ป้องกัน Decimal Truncation พร้อมผูก `job_no` ลง Stock Card เป็น Reference
156. AR Knock-off & Deposit Allocation (Phase 17 Completion): สร้างระบบรับชำระเงิน (REC) รองรับการหักมัดจำ (DEP_IN) แบบ Real-time พร้อมปรับปรุง UX เปลี่ยนชื่อคอลัมน์เป็น "ยอดหนี้ที่ต้องการตัด (รวมมัดจำ)" ป้องกัน Human Error ตามหลัก SAP FI-AR
157. SAP-Standard Document VOID Engine (Phase 18): สร้างฟังก์ชันยกเลิกเอกสารแบบ Atomic รองรับการทำ Inventory Reversal คืนสต็อกเข้าคลัง (IN) อัตโนมัติ โดยอ้างอิงจาก document_items (Source of Truth) พร้อมบังคับระบุเหตุผล (remark)
158. Enterprise Credit Note (CN) Architecture (Phase 18): พัฒนาระบบใบลดหนี้ที่ครอบคลุม 2 กรณีหลัก: 1. รับคืนสินค้า (Return Goods - ตีสต็อกกลับเข้าคลังและล็อกราคาเดิม) 2. ชดเชยราคา (Price Adjustment - ลดหนี้โดยสต็อกไม่เคลื่อนไหว ปลดล็อกช่องราคาให้แก้ไขได้)
